## 1. 验证方法论：从「我推公式」改成「分层校验栈」

### 1.1 现状与弱点（实测）

`验证报告/z2c_conv/verify_ops.py::check()` 只有**两个判据**：

```python
got_remove = base_vol - part.volume      # ① 体积，容差 0.5 mm³（过严）
ok = dv < 0.5 and radii_ok              # ② 圆柱面半径集合含预期值
```

其中 **`expect_remove`（期望去除量）和 `base_vol`（基体体积）都是我手推/手写的**。

**→ 三个栽的案例，全都错在"我的期望值"而不是算子本身：**

| 栽的地方 | 真正错的是 | 本该由哪类断言抓住 |
|---|---|---|
| `chamfer` 结果翻倍 | 选边谓词同轴过滤 → 选了 4 条边而非 2 条 | 结构断言（断言选到几条边） |
| `box` 选 0 条边 | `Box()` **默认居中**，坐标系假设错 | 前置 bbox 断言 |
| `csk` 差 `π(cs_r−r)r²` | 沉孔是**圆锥不是圆台**（几何语义错） | 面类型断言（存在 CONE 面） |

### 1.2 调研结论（论文 + GitHub，2026-10-15）

**(a) Zero-to-CAD 论文自己的框架**（arXiv 2604.24479 §4.3）——**它不推期望值，用性质断言**：

| 阶段 | 内容 |
|---|---|
| 代码执行验证 | 隔离子进程 + 超时；异常带完整堆栈回喂模型 |
| 几何验证 | ① 拓扑有效（无自相交/退化面）② **恰好一个连通实体** ③ **≥ 7 个 B-Rep 面（防平凡解）** ④ 正体积 |
| **导出验证** | 导 STL **和** STEP —— 抓前两阶段漏掉的**面朝向错误 / 不支持的边配置** |

- **反 hack 纪律**：系统提示明确要求模型**绝不通过"简化代码"来修复**（防"删特征直到验证通过"）。
- **统计**：首试成功率仅 **22.3%**，成功前平均 **3.30 次**尝试。
- **评估**：体素化 IoU（64³，按 45° 增量旋转取最大以消歧）+ Chamfer Distance + 成功率；
  并明确 **"success rate alone is insufficient：永远返回 trivial box 的模型成功率 100%"**。

**(b) GitHub 两个 LLM-CAD 项目**

| 项目 | 可抄的做法 |
|---|---|
| `0okevino0/claude-cad` | `BRepCheck_Analyzer(...).IsValid()` assert + `len(Solids())==1` + volume/bbox；**逐步骤检查**定位第一次失效那一步；**期望体积由参数推导 + ±15% 宽带**。金句：**"green [OK] 只代表 Python 跑完了"**、**"绝不要跑完把 `Volume()` 贴回去当期望"** |
| `sameerreddy789/Text2Cad` | **合法 ≠ 正体积**——`BRepCheck_Analyzer` 对**负体积的壳**也可能返回 True，必须 `IsValid() and volume > 0`；**每个布尔结果都要过闸**（坏拓扑会潜伏到下一次布尔才爆 `Null TopoDS_Shape`） |

**(c) 通用测试界**：**变形测试（Metamorphic Testing）**——T.Y. Chen 1998 提出、750+ 论文，
**专治 oracle problem**（正是"期望值要自己推"的困境）。GeoMetaMorph 给出四类几何不变量：
**镜像 / 缩放 / 旋转 / 平移**。

**(d) ⚠️ 差分测试的修正**：build123d 与 FreeCAD **底层都是 OCCT**（FreeCAD 容差 1e-7mm），
所谓"双引擎交叉"实为**同内核两套绑定** → **独立性有限**（抓得到 API 层错，抓不到内核层错）。
真差分需不同内核（Parasolid / ACIS / CGM），我们没有。

**(e) 内核自带"真值检查"（不需推任何公式）**：`Shape.isValid()` = `BRepCheck_Analyzer(...).IsValid()`；
另有 `Part.CheckGeometry`、亏格/欧拉示性数 V−E+F、`GProp` 体积/质心/惯性矩。

### 1.3 建议：分层校验栈

| 层 | 检查 | 依赖手推公式？ | 现状 |
|---|---|---|---|
| **L0** 执行成功 | 代码跑通 | ❌ | ✅ 有 |
| **L1** 内核合法 | `isValid()` + 单实体 + **`volume > 0`**（防朝向翻转） | ❌ | 🔶 缺 `volume>0` |
| **L2** 结构断言 | 面类型/数量、bbox 不变式、**最少面数（防平凡解）** | ❌ | 🔶 缺最少面数 |
| **L3** 变形关系 | 镜像/缩放/旋转/平移不变量；参数比例关系 | ❌（只需关系） | ❌ 没有 |
| **L4** 量级比对 | 期望值由参数推导，**±15% 宽带** | ✅（但宽） | ⚠️ **现在只靠这层，且容差过严** |
| **L5** 端到端保真 | **IoU / Chamfer Distance**（模型 vs 原图） | ❌ | ❌ 没有（`diff_images.py` 是雏形） |
| **L6** 变异测试 | 算子换 no-op → **必须 FAIL** | ❌ | ❌ 没有 |

**成本**：L1/L2/L4/L6 加进 `verify_ops.py` ≈ 1–2 小时（实验区，不碰主干）；
L3 需要为每类算子声明不变量关系 ≈ 半天；L5 要接 `diff_images` 类工具 ≈ 1 天。
**验收**：19 条验证在"故意把算子换成 no-op / 参数减半"时**必须 FAIL**。

## 2. 投影原则定边定面（跨视图签名）

### 2.1 现状：只有"半套"，且只在包围盒层面

`steps/s6b_projection.py::check()` 已实现三大投影原则，但比的是**整体包围盒**（3 个标量等式）：

| 原则 | 现在的判定 |
|---|---|
| 长对正 | Front 的 x 长度 == Top 的 x 长度 |
| 高平齐 | Front 的 y 高度 == Right 的 y 高度 |
| 宽相等 | Top 的 y 宽度 == Right 的 x 宽度 |

**⇒ 它是"校验"（整体对齐），不是"定位"（逐特征/逐边对应）。**

### 2.2 构想：把它升级成定位器

```
anchor = {
  "view": "Front",
  "local": {"kind": "circle", "r": 4},
  "cross": [                                     # ← 跨视图约束
     {"view": "Top",   "axis": "x", "at": -22.5},   # 长对正
     {"view": "Right", "axis": "y", "at": 27.0},    # 高平齐
  ]
}
```

匹配流程：**本视图找候选 → 把候选的 3D 位置投影到其它视图 → 该处必须确实有对应几何 → 确认同一特征。**

### 2.3 实测到的动机：单视图谓词有真歧义

bracket 的锚点与实测：

```
D9 的谓词 = {kind: circle, r: 4.5}
Top 视图里 r=4.5 的圆有 2 个：(-22.5, -11.0) 与 (22.5, -11.0)
⇒ 谓词同时命中 2 个；first_circle_r() 只是"取第一个"
⇒ 因两孔同径，没有任何检查能告诉你标的是哪一个
```

### 2.4 双价值：定位 + 预防

- **定位**：消歧义（同视图多个同径圆）、抗 TNP（参数变了按参数重定位）、几路交叉确认。
- **预防**：`D8_wall` 那个真 bug——立板孔**轴沿 X**，在 Front 视图里**不是圆而是直线**，
  所以它被静默跳过。若先按投影原则推"该孔在各视图应投影成什么"，**就不会去 Front 找圆**。

### 2.5 已有积木与拦路点

| 已有 | 提供什么 |
|---|---|
| `s6b_projection` | 视图 ↔ 模型轴的对应关系 |
| `s2_drawing` 的 `VIEWS[].dir/xdir` | 投影方向 |
| `s2_drawing` 的 `PLACE=(x,y,flip)` | 摆放与翻转 |
| `tools/anchor_verify.py` | 谓词匹配 + 存在性/指对性双校核 |

**⚠️ 拦路点：坐标系没统一。** `_drawing.json` 里 `view.edges` 的 y 是**居中**
（Right 视图 y ∈ [-18.5, 18.5]），而 `dims` 的 `y1/y2` 是**从底面量起**（0 → 27）——
差一个 offset（这正是 s5b 当时改用"区间宽度"而非绝对位置比较的原因）。
**跨视图签名必须先做「视图局部坐标 ↔ 模型坐标」映射**（含居中/flip/scale）。**这是主要工作量。**

### 2.6 三步落地

| 步 | 内容 | 估时 |
|---|---|---|
| **S1** | `s6b` 从"包围盒"细化到"**逐标高/逐条对应**"（Front 每条水平线的 y，须能在 Right 找到同 y 的线/点）——兼作校验增强 | 半天 |
| **S2** | **统一坐标系**（视图局部 ↔ 模型坐标映射函数）——前置条件 | 1 天 |
| **S3** | 锚点 schema 升级为「本视图谓词 + 跨视图约束」；`anchor_verify` 支持多视图联合匹配；替换 `first_circle_r` 的"取第一个" | 1–2 天 |

**验收件**：bracket 的 **2-φ9**（同视图两个同径圆）——升级后应能分别定位到具体哪一个。

### 2.7 边界（三条）

1. **遮挡**：隐藏边不出现 → 跨视图约束只能要求"**出现时一致**"，不能要求每个视图都有；
2. **轮廓边 ≠ 解析边**：圆柱侧影在投影里是**直线**，签名要区分两类；
3. **剖视 / 局部放大**：不适用标准投影关系，需单独处理。

## 3. 同步点与单源生成

### 3.1 问题

一个算子概念现在要写在 **≥ 4 处**：`lib/ir.py::TREE_OPS`（声明）+
`tools/ir2build.py`（build123d 生成）+ `tools/ir2partdesign.py`（FreeCAD 生成）+ 验证。

### 3.2 ★ 实测硬伤（只读扫描）

| 项 | 实测 |
|---|---|
| `TREE_OPS` 声明 | 6 个真算子：`Sketch` `Pad` `Pocket` `Fillet` `Chamfer` `Hole` |
| **生成器未实现** | **`Pocket`（ir2build 无）、`Fillet`/`Chamfer`（ir2build 只有 PLACEHOLDER 注释）、`Hole`（两个生成器都 0 处）** |
| `validate()` 校验范围 | **只校验 `tree` 层（`lib/ir.py:158-161`），从不看 `impl`** |

**⇒ 而 `ir2build` 生成几何读的正是 `impl`。所以：**
**一份"校验通过"的 IR，可以生成出少了特征的零件，`ir2build` 仍 exit 0、不打任何警告。**

### 3.3 危害（四种）

| # | 危害 | 实例 |
|---|---|---|
| 1 | **漏改一处 → 静默错误 → 假通过** | `s6b`/`s5b` 同源 `_load_json_opt` 只修一处 → bracket 拿垫片数据判 pass |
| 2 | 声明与实现漂移 | 见 §3.2（4/6 未实现） |
| 3 | 回归成本高 → 人会跳过验证 | 改 lib 一处 → 联动 4 处 + 重跑 5 个零件 |
| 4 | 语义重叠 → 模型选错 | `hole/cboreHole/cskHole`、`rarray/polarArray/pushPoints`、`cut/cutBlind/cutThruAll` |

### 3.4 判据与解法

- **判据：**「加一个算子要改几个文件？」——是 **1** 就随便加；是 **4** 就先做单源生成（**我们现在是 4**）。
- **单源生成**：算子定义只写**一处**（注册表条目含 `tree_op` / build123d 表达式 / freecad 映射 / 验证），
  词表与两个生成器**从它派生** → 4 处压到 1 处。`验证报告/z2c_conv/op_lib.py` 的 `DISPATCH` 已是雏形。
- **边界**：两后端不同构（同一概念写法/名字/参数不同）→ 注册条目里仍要写**两套实现表达式**，
  但**在同一个位置**，改动是原子的；某后端不支持的算子应**诚实声明不支持**，不硬凑。
- **成本**：收 15 个算子进注册表 ≈ 1 小时；两个生成器改查表 ≈ 1–2 小时；一致性检查 ≈ 30 分钟。

## 4. FreeCAD 能力盘点（三层落差）

### 4.1 实测（FreeCAD 1.1.0，`freecadcmd` 只读探测）

- **`PartDesign::` 可创建 35 种**：`Body` `Pad` `Pocket` `Revolution` `Groove`
  `AdditiveLoft` `SubtractiveLoft` `AdditivePipe` `SubtractivePipe` `AdditiveHelix` `SubtractiveHelix`
  **`Thickness`（抽壳）** **`Draft`（拔模）** `Fillet` `Chamfer` **`Hole`**
  `Mirrored` `LinearPattern` `PolarPattern` `MultiTransform` + 基元若干。
  （`Shape` / `Clone` 不可用）
- **`Part::` 可创建 21 种**：含 `Extrusion` `Revolution` `Loft` `Sweep` `Thickness` `Offset` `Cut` `Fuse` `Common` 等。
  （`Tube` / `CompoundFilter` 不可用）

### 4.2 映射对照（同构但名字/参数不同）

| 我们的算子 | FreeCAD |
|---|---|
| `shell` | `PartDesign::Thickness` |
| `sweep` | `AdditivePipe` |
| `loft` | `AdditiveLoft` |
| `rarray` / `hole_grid` | `LinearPattern` |
| `bolt_circle` | `PolarPattern` |
| `mirror` | `Mirrored` |
| 孔向导 | `Hole` |

### 4.3 三层落差（关键区分）

| 层 | 数量 | 谁决定 | 现状 |
|---|---|---|---|
| ① FreeCAD 平台能力 | 数百命令 / ~30 工作台 | FreeCAD | 很宽 |
| ② 我们的 IR 词表 | ~20–30 | **我们**（按 10 万零件覆盖率选 + 克制） | 窄，但是**主动选择** |
| ③ 已接入后端 | ir2build: extrude+6草图+5tool+cut；ir2partdesign: 仅 Pad/Pocket | 我们 | **最窄 = "还没做"** |

**⇒ "缺算子"的准确说法是 ② 比 ① 窄（我们没暴露），不是 FreeCAD 没有。**
（"命令多"来自 ~30 个工作台，其中只有 `Part`/`PartDesign`/`Sketcher` 属机械零件实体建模；
Draft 是建筑向 2D、Surface/Mesh 是曲面网格、BIM/CAM/FEM/Robot 非本场景、TechDraw 属出图层。）

**⇒ 对 D 阶段（IR→PartDesign）的意义**：FreeCAD 侧**有挂点**（真特征树 + 参数化），
可行性比早先估计的更高；瓶颈在"IR 词表怎么定 + 4 处同步"，不在后端能力。

## 5. 算子该「进词表」还是「写逃生口」

### 5.1 实测基线

| 侧 | 行数 |
|---|---|
| 手写一个零件的 `s1_build.py` | **91–137 行**（bracket 91 / gasket 110 / ybracket 118 / lbracket 137，均值 ~114） |
| 算子实现 | **~15–20 行/个**（`op_lib.py` 290 行含 15 算子 + 演示） |

### 5.2 成本结构与阈值

- **逃生口 = 每零件线性消耗**（N 个零件 N 倍）；**进词表 = 一次性**（与零件数无关）。
- 验证跑本地（0 token）；烧 token 的只有"写实现那一段"。
- **阈值：同一算子被 3–5 个零件用到就值得进词表**；只出现 1 次的长尾（`rib` 0.2% / `draft` ≈0%）
  走逃生口。

### 5.3 摊平麻烦的关键

**不必一开始就决定加不加算子**：

```
手写逃生口跑通（不阻塞）→ tools/recorder.py 录成 IR（script→IR 已通）
  → 同一模式出现 2–3 次 → 泛化成算子 → 进词表 → 之后同类零件只填数据
```

⇒ **写一次 Python 不浪费（会被录成 IR 沉淀）；真正浪费的是"每次都重写一遍不沉淀"。**

## 6. Zero-to-CAD 出身澄清（影响词表结论的措辞）

数据集卡权威信息（`验证报告/z2c_100k.json`）：

- 全名 `ADSKAILab/Zero-To-CAD-100k`，作者 **Autodesk Research**；
- 论文标题：**"Zero-to-CAD: Agentic Synthesis of Interpretable CAD Programs at Million-Scale
  *Without Real Data*"**；
- 标签：`synthetic-data`、`agentic-AI`、`CadQuery`、`construction-sequence`、`curated`。

**⇒ 它不是"人工绘图手法的命令集"，是 AI agent 合成的程序。**

数据侧自证（10 万条实测）：6772 个不同 `op_name`，**71.5% 只出现在 1 个零件里**；
**1601 个自定义辅助函数**；**3054 个 CamelCase 零件概念名**（`OxygenSensorMount` / `PistonSkirt` …）。

**对结论的影响：**

1. "top-30 覆盖 84%" 的准确表述是「**在这批合成数据里**，agent 常用构造就这 30 个」；
2. **仍然有效**：它反映 **CadQuery API 用法分布**，而 CadQuery 语义与人类建模语义高度对应
   （与 SolidWorks 命令表 18 条命中 14 条）⇒ **用频率定"先做哪些算子"的依据成立**；
3. **必须打的两个折扣**：① `Without Real Data` → 形状分布未必等同真实零件库；
   ② **agent 代码会错**（实测同 uuid：代码描述 100 宽 vs step 70 宽）⇒
   **"高频" = "agent 常这么写"，不是"正确答案"**，数值绝不能当真值。
