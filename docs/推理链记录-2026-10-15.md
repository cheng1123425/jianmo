## 决策 1 · IR 在架构里的定位：唯一真值源，还是又一个中间层？

**背景**：接手时 `lib/ir.py` 已存在（另一位开发者写的），但 `s0b_dwgread` 之类步骤要么在用图纸、要么在用代码，IR 处于"有 schema、没接线"的状态。

**候选**：
- (a) IR 作为**唯一真值源**，所有步骤都从 IR 派生；
- (b) IR 只是"录制产物"，可随时从脚本重建；
- (c) 维持现状，IR 只当文档。

**推理**：
1. 问"如果 IR 明天被删，会坏掉什么？"—— 若只是录制产物，删了能从脚本重建 ⇒ 那它**没有架构地位**。
2. 另一位开发者的 HANDOFF 已定案"IR 当唯一真值源"，但**当时 C/D/E/G 全部未做** ⇒ 定案缺少支撑。
3. 关键检验：**双向都要能跑通**。`script→IR`（录制器）只能单向，**"改 IR → 全链路跟着变"就永远是口号**。

**决定**：采用 (a)，并且**把"双向闭合"设为完成标准**，而不是"把 IR 做完"。

**事后验证**：C 阶段往返自测体积差 **0.0**、面数 65 一致 ⇒ 定案有了硬证据，不再是口号。

**置信度**：高。**若被推翻**：若实测发现 IR 表达不了某类零件且逃生口被频繁使用，则应退回 (b)（IR 仅作可选加速层）。

## 决策 2 · 全量重算 vs 增量重建

**候选**：(a) 每次改参数重跑整条链；(b) 只重算受影响的特征（SolidWorks 式 Ctrl+Q）。

**推理**：
1. 增量需要**特征间依赖图 + 稳定命名**——而稳定命名恰恰是 TNP（拓扑命名问题），**没有解**。
2. 我们的路线是"代码即特征树"，靠**条件查询**（`faces().sort_by(Axis.Z)[-1]`）取代身份引用 ⇒ 已经绕开 TNP，但**没有增量所需的稳定标识**。
3. 增量还会引入"这次到底重算了没有"的新判断题——而**沉默的错误**是我当天反复识别的头号危害。

**决定**：**(a) 全量重算**，并明确"改参数 = 重跑整条流水线"。

**代价**：慢（这也是 `s0b_dwgread` 占 95% 耗时的痛点来源）。

**置信度**：高。

## 决策 3 · 标注锚点：用几何谓词，不用 `Edge#N`

**背景**：README §3 规范说尺寸要用 `References2D` 引用投影边，`EdgeN` 用 `getVisibleEdges()` 的 0-based 下标。

**问题**：`EdgeN` 是**索引**，几何一变就错位（TNP）。

**候选**：(a) 存 `Edge#N`（README 规范）；(b) 存**几何谓词**（`{kind:circle, r:4}` / `{kind:extent, axis:x}` / `{kind:level_pair, r:4, axis:x}`）；(c) 存特征 id + 参数。

**推理**：
1. 索引在任何参数变化后失效 ⇒ **不是持久引用**。
2. 谓词是**几何不变量**：参数变了，谓词的"半径 4"仍能定位到正确的圆（半径本身随参数变，但**匹配是相对量**）。
3. (c) 最强，但要求"从参数反推该边在投影里的位置"，实现成本高且会重新引入坐标约定问题。

**决定**：**(b)**，并在实现里**明确注释"绝不存 Edge#N"**作为纪律。

**事后验证（意外收获）**：谓词机制第一天就抓出 `D8_wall` 长期 bug——立板孔**轴沿 X**，而代码去 **Front 视图**（沿 Y 看）找 r=4 的圆；孔在正视里是**直线**，`first_circle_r()` 返回 None，该标注**从加进来那天起就被静默跳过**，而闭环一直报 pass。
**推理价值**：旧代码因为"宽容地跳过"把问题藏了很久 ⇒ **谓词把"该在哪儿出现"变成了可断言的东西**。

**置信度**：高。

## 决策 4 · 内腔不可见特征：用真剖视，还是继续"特例放行"？

**背景**：IR 纪律第 5 条写着"内腔不可见 → 特例放行并在 note 留痕"（因为 ybracket 沉孔底在三视图里没有 2D 边可挂尺寸）。

**候选**：(a) 继续特例放行；(b) 加"辅助视图/剖视"出图能力；(c) 放弃这类标注。

**推理**：
1. 特例放行的代价：**内腔尺寸永远进不了图**，而内腔恰是图纸信息量最大的部分（沉孔深度、开口宽度）。
2. 冒烟实测发现 **FreeCAD 1.1 有 `TechDraw::DrawViewSection` + `DrawHatch`**，且**剖视参数全是普通属性**（`SectionOrigin`/`SectionNormal`/`SectionSymbol`…）⇒ **可以数据化**。
3. 结论：这不是"代码需求"，是**"数据选项"** ⇒ 值得做。

**决定**：**(b)**，并把剖视做成 `draw_spec.VIEWS[].type="section"` —— **数据选项，不是代码**。

**实测坑（决定可行性）**：`BaseView` 必须设（否则 0 边）；`SectionOrigin` 要落在**实体内部**（设在表面 Y=0 切空）；剖面线属性名是 `Source`；`XDirection` 不能设 None。

**代价**：`lib/drawing_fc.py` +45 行（纯加法），回归 5 个零件。

**置信度**：中高。**若被推翻**：若剖视在某些零件上产生"剖切线穿过特征"导致标注错位，则应退回"特例放行 + 在标题栏注明剖切位置"。

## 决策 7 · 尺寸链误报：改数据还是改判据？

**情境**：bracket 报 `Σhead_h+arm_h = 41 > 跨度 37`（closure error）。

**候选**：
- (a) 改 bracket 的 `ref_spec`（声明值）让它闭合；
- (b) 改校验逻辑：先判"这组标注是不是链"，不是链就别求和；
- (c) 把该 error 降级成 warn/info（最省事）。

**推理**：
1. 先查**几何端点**：`head_h` 是 `y1=0→27`、`arm_h` 是 `y1=0→14` —— **两者都从底面量起**，是**同一基准的并联标注**（坐标式标注，国标合法写法）。
2. Σ=41 **没有几何意义** ⇒ **错的是校验器的隐含假设**（"同 (view,axis) 的标注都是链"），不是数据。
3. (c) 最省事，但**单指标必被 hack**（论文原话："永远返回 trivial box 的模型成功率 100%"）—— 只降级不补检测 = **净损失**。

**决定**：**(b) + 补一条与链无关的精确判据**（`seg_exceeds_span`：单条标注长度 > 视图跨度 → error）。
- 用**已有几何端点**判链（`_seg_interval` / `_has_overlap`）：有重叠 ⇒ 不是链 ⇒ 只记 `info`。
- **同时补回检测力**，这是我给自己定的纪律：**放宽校验必须补等价检测力**。

**事前预判**：`s7_decide` 只把 `severity=="error"` 当阻断 ⇒ 把假报降为 info 就能解 manual。**但必须先确认那是假报**——所以我先查了端点坐标才动手。

**结果**：bracket / ybracket **manual→pass**，其余三件不变。

**置信度**：高。

## 决策 8 · 算子做多少：追长尾还是克制？

**候选**：(a) 全接入；(b) 做 30–50 个；(c) 只做 top-10。

**推理**：
1. 先测**词表完备度曲线**（"零件的几何算子全在 top-K 表内"的占比）：K=20→65%、**K=30→84%**、K=50→88.5%、K=100→94.5%。
2. 边际收益：从 30→50（+20 个）只换 **+4.5%** 覆盖，**成本却是 +67% 维护面**（每算子 4 个触点）。
3. 剩下的 5.5% 要靠 **3500+ 个罕见算子**（`rib` 0.2%、`draft` ≈0%）——**永远追不完**。

**决定**：**(b) 但落在 30 这个拐点**；长尾走**手写 `s1_build.py` 逃生口**（数据驱动与手写代码**共存**，不是二选一）。

**配套纪律**：先量化"单算子占地"（实测 ~25–35 行）才谈"臃肿"——50 个 ≈ +1750 行 ≈ 现存 19%，**绝对量不算臃肿**。真正的成本是**同步点**。

**置信度**：中高。**若被推翻**：若真实项目里带筋/拔模/曲面的零件占比远高于 0.2%（例如液压/注塑行业），则该补进词表。

## 决策 9 · 手写逃生口 vs 加进词表：判据是什么？

**推理**：先算清**成本结构**，而不是凭感觉。
- 实测：手写一个零件 `s1_build.py` = **91–137 行**；算子实现 = **~15–20 行**。
- **逃生口是每零件线性消耗；进词表是一次性、与零件数无关。**

**决定**：给出**阈值判据**——同一算子被 **3–5 个零件**用到就值得进词表；只出现 1 次的长尾走逃生口。

★ **更重要的一条（元决策）**：**不必一开始就决定加不加算子**。先手写逃生口跑通 → `recorder.py` 录成 IR → 同一模式出现 2–3 次 → 泛化成算子。
**推论**：**写一次 Python 不浪费（会被录成 IR 沉淀）；真正浪费的是"每次都重写一遍不沉淀"。**

**置信度**：高。

## 决策 10 · 验证：继续手推期望值，还是换判据？

**触发**：用户直接点出"我在 chamfer/box/csk 上栽 3 次"。

**推理**：
1. 复盘三次栽，**共同点是"错的是我的期望值，不是算子"**：
   - chamfer 翻倍 → 是**选边谓词**选了 4 条（不是公式错）
   - box 选 0 边 → 是**坐标系假设**错（`Box` 默认居中）
   - csk 差 `π(cs_r−r)r²` → 是**几何语义**错（圆锥 vs 圆台）
2. ⇒ **把正确性押在我手推公式上，本身就是设计缺陷**。
3. 查论文（Zero-to-CAD §4.3）发现同领域**根本不推期望值**，用**性质断言**：拓扑有效 / 单实体 / ≥7 面 / 正体积。
4. 查 GitHub 两个 LLM-CAD 项目，同一条共识：**"green [OK] 只代表 Python 跑完了"**、**"期望值由参数推导 + ±15% 宽带"**、**"合法 ≠ 正体积"**。
5. 查测试界：**变形测试（MT）专治 oracle problem**——不预测输出，验证"多次运行之间的关系"。

**决定**：提出 **L0–L6 分层校验栈**：
- **L0–L3 与 L6 都不依赖我推公式**（执行/内核合法/结构断言/变形关系/变异测试）；
- **我手推的解析式降级为 L4「宽带量级校验（±15%）」**，不再是唯一判据。

**同时纠正自己**：上一条提的"双引擎交叉"——**build123d 与 FreeCAD 都是 OCCT** ⇒ 独立性有限，抓不到内核层错。

**置信度**：高。**未实施**（用户说"先不做"），已入待办 #6。

## 决策 11 · 定边定面：单视图谓词够不够？

**触发**：用户提出"能不能用投影原则定边定面"。

**推理**：
1. 现状：`s6b_projection` 已实现三大投影原则，**但只比整体包围盒（3 个标量等式）** ⇒ 是**校验**不是**定位**。
2. 现场验证单视图谓词的弱点：bracket 的 `D9 = {circle, r:4.5}`，而 Top 视图里 **r=4.5 的圆有 2 个** ⇒ 同时命中 2 个，`first_circle_r` 只是"取第一个"；**因同径，没有任何检查能告诉你标的是哪一个**。
3. 投影原则能提供**跨视图约束**（长对正/高平齐/宽相等）⇒ 把"哪个是哪个"钉死。
4. 附加价值：**能预防"视图选错"**——若先按投影原则推"该孔在各视图应投影成什么"，就不会去 Front 找圆（`D8_wall` bug 的根因）。

**决定**：采纳，列为 **S1/S2/S3 三步**（逐条对应 → 统一坐标系 → 跨视图签名）。
**并明确拦路点**：`view.edges` 居中坐标 vs `dims` 从底面量起，**差一个 offset**（这正是我修 s5b 时改用"区间宽度"的原因）⇒ **S2 统一坐标系是硬前置**。

**置信度**：中高。**若被推翻**：若剖视图/局部放大视图占比升高，标准投影关系不适用，需先给视图加"是否参与跨视图约束"的标记。

## 决策 13 · 优先级：先做 50 分钟的止损，还是先做单源生成？

**情境**：待办里"一致性检查（30 min）""validate 校验 impl（20 min）""单源生成（半天）""18 算子接入（半天）"。

**推理**：
1. 先问**"哪条不做会持续造成损失"**——`TREE_OPS` 4/6 未实现 + `validate()` 不看 impl，意味着**"校验通过"≠"能生成"且 exit 0 不警告**，这是**正在发生的静默错误面**。
2. 而"算子接入"是**能力扩展**，不做只是"能力不够"，**不会让已通过的检查变得不可信**。
3. ⇒ **止损优先于扩展**；且止损是**只加检查、不动生成逻辑**，风险最低。

**决定**：把「一致性检查 + validate 校验 impl」列为 **P0（约 50 分钟）**，单源生成排在它之后（也是算子接入的前置）。

**用户反馈**：用户要求"先不要加，先上传" ⇒ **已接受，把两条挂起并写进待办**。

**置信度**：高。
