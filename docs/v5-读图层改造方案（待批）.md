## 〇、一句话诊断

**s0b 在栅格（PNG）路径上基本是空转的。**
五个零件的 `dwg_semantics.json` 全部 `mm_per_px=0.0`、`dims=[]`、`annotations=0`、`match_rate=0.0`。
判据的输入（标定后的标注、图层、视图角色）一个都不存在，所以「给 s0 加机械制图判据」这件事
**在栅格路径上无处落脚**——不是判据不够，是没有料。

## 一、实测证据

### 1.1 语义产出横向对比（`parts/*/notes/dwg_semantics.json`）

| part | mm_per_px | circles | dims | match_rate | annotations | 顶层键 |
|---|---|---|---|---|---|---|
| acc_plate | 0.0 | 2 | 0 | 0.0 | 0 | mm_per_px, scale_method, summary, circles, dims |
| bracket | 0.0 | 7 | 0 | 0.0 | 0 | 同上 |
| gasket | 0.0 | 6 | 0 | 0.0 | 0 | 同上 |
| lbracket | 0.0 | 5 | 0 | 0.0 | 0 | 同上 |
| ybracket | 0.0 | 2 | 0 | 0.0 | 0 | 同上 |

- `summary.lines` 有计数（bracket 88 条），但**没有 `lines` 数组落盘**——线段数据拿不到。
- `circles[0]` 的 `r_mm = 0.0`——标定没跑，所以半径没换算成毫米。
- 无 `layers`、无 `views`、无标注角色字段。

### 1.2 下游怎么"处理"了这份空语义

| 步骤 | 对 dwg_semantics 的态度 | 后果 |
|---|---|---|
| `s0_plan` | **不读**（读 params / dims_spec / ref_spec / plan_src） | 方案完全建立在人的输入上 |
| `s5b_dimchain` | 读，但 `dims=[]` 时走「没有图纸语义输入，跳过尺寸链校验」 | **静默跳过** |
| `s6_compare` | **不读**（只 exec `ref_spec.py`） | 基准 = 人抄的原图 |
| `s6b_projection` | 不读（校验模型自出图的自洽） | 三视图一起错也全绿 |

### 1.3 结构结论

整条链里，**原图只被 s0b 碰了一次，而且这次碰失败了**；
之后 params / ref_spec / dims_spec 全是人抄，s2 自出图、s5 自己提特征、s6b 自己查自己 —— **全是自环**。

这与外罩 #1（`48.5±0.1` 被当总高）的机理完全吻合：
标注角色（定形/定位/总体）既没被机器读出来，也没被强制要求人标注角色，
于是那个数字在两个地方都能自圆其说。

## 二、根因（结构性，不是单点 bug）

1. **标定失败被吞掉**：`mm_per_px=0.0` 不报错，后续所有换算静默产出 0。
2. **标注层在栅格上不可用**：`dims=[]` 不是"没找到"，是"这条路走不通"，但两者输出一样。
3. **`s5b` 的跳过是静默的**：项目已经吃过两次"假通过"（s6b 误读垫片 `_drawing.json`、s5b 尺寸链假 error），
   这次是同一类病的第三次 opportunity。
4. **缺中间字段**：`dwg_semantics` 没有「图层 / 视图 / 标注角色 / 特征类型」，
   任何依赖这些概念的下游判据都无从触发。
5. **`s0_plan` 的 `skill_advice` 接口在 `pipe.py` 里没接线**，且是 `?` 可选 —— 判据即使写了也不跑。

## 三、改善方案（分 5 期，按依赖排序）

### 第 0 期：让失败变响（**先做这个，其它全部依赖它**）

不做任何识别能力提升，只做一件事：**把静默失败改成显式状态**。

| 动作 | 判据 |
|---|---|
| `s0b` 产出加 `status` 字段：`ok` / `degraded_no_scale` / `degraded_no_dims` / `failed` | — |
| `mm_per_px == 0` → `status != ok`，并写进 `errors.md` | — |
| `dims` 为空 → `status` 至少 `degraded_no_dims` | — |
| `s5b_dimchain` 跳过时**必须**产出一条 warning 级判定，不能只写日志 | — |
| `s6_compare` 在 `status != ok` 且 `ref_spec` 无 `derived_from` 标注时，输出「基准来源不明」 | — |

**验收判据**：五个零件跑完 s0b，`status` 全为 `degraded_*`；闭环**不再报 pass**，
而是报「输入层降级，闭环结论不可信」。这一步会让当前的全 pass 基线掉下来——**这是预期结果**，
因为现在的 pass 是自环出来的。

> ⚠️ **风险与反对意见**：这会"打掉"现有的绿色基线。
> 我的判断是绿色基线本身是假的（证据：1.3），但**这是需要你拍板的第一步**，不是我能替你定的。

### 第 1 期：栅格路径的定位（决策，不是编码）

两条路，只能选一条：

| 方案 | 内容 | 代价 |
|---|---|---|
| **A. 承认栅格只做粗筛** | 栅格路径只负责「轮廓大致在哪、圆在哪」；**标注一律由人填 `dims_spec`，且必须带角色** | 最小；立刻可做 |
| **B. 补栅格的标注层** | OCR + 字形分类 + 引线追踪，做出 dims | 大；且**必然输给矢量路线** |

**我的判断是 A。** 理由：

1. 另一台机器 10-15 23:30 已经用实测否掉了「PNG → 矢量 → 再识别」这条路：
   **矢量化不解决标定问题**（输出的还是像素坐标），下游的拟合圆/识别文字正是栅格解析器做不好的事。
2. 真正能解决标定的是**原生矢量输入**：10-16 23:46 实测 DXF `$INSUNITS=4`（毫米）、
   矢量 PDF 读到 77 条文本 / 每图层实体数（尺寸线层 482、粗实线层 160、中心线层 105、剖面线层 83）。
   **图层信息是矢量路线白送的，栅格路线要靠线宽聚类去猜。**
3. 栅格路径不能删——它还要应付教材截图、拍照这类只有位图的输入。但它的正确定位是**降级入口**，
   而不是主力。

> 注意：DXF/矢量工具链**按你的要求不进项目**（10-16 00:04「不要加到项目中去，记录一下就好」）。
> 本方案只改 `s0b` / `s0_plan` / `s5b` / `s6_compare` 这四个**已在主干**的步骤，不引入新工具链。

### 第 2 期：字段补全（让判据有落脚点）

`dwg_semantics.json` 增加：

```jsonc
{
  "status": "ok|degraded_*|failed",
  "scale":  { "mm_per_px": 0.0, "method": "insunits|labels|least_squares",
              "residuals": [], "source": "vector|raster" },

  "views":  [ { "name": "Front", "bbox": [x0,y0,x1,y1],
                "axes": { "h": "X", "v": "Z" } } ],       // ← 视图分区 + 轴向

  "layers": { "coarse": [], "fine": [], "center": [],   // ← 线型（栅格靠线宽猜，矢量直接给）
              "section": [], "dim": [] },

  "lines":  [ { "p1": [x,y], "p2": [x,y], "layer": "coarse", "view": "Front" } ],  // ← 现在没落盘
  "circles":[ { "c": [x,y], "r": 106.0, "r_mm": 0.0, "layer": "coarse", "view": "Front" } ],

  "annotations": [ {
      "raw": "Ø12", "value": 12.0, "kind": "diameter|radius|linear|angular|thread",
      "view": "Top", "tolerance": "±0.1",
      "role": "defining|locating|overall",        // ★ 缺的就是这个
      "applies_to": "boss|hole|flange|overall",   // ★ 它管哪个形体
      "evidence": { "p1": [x,y], "p2": [x,y] }    // 箭头端点，供复核
  } ],

  "features": [ { "type": "obround", "len": 21.0, "dia": 6.0,
                  "center": [x,y], "view": "Front" } ]   // ← 长圆孔等特征级
}
```

**★ 关键字段是 `role` + `applies_to`。**
`s0b` 现在的 `dims` 只有"值"没有"角色"，所以 `48.5` 既能解释成总体高、也能解释成台阶标高——
**判据无从裁决**。补上角色，`dimension-mapping.md` §1 的三角色校验
（"每个方向总体尺寸只有一个"）才能跑。

### 第 3 期：接判据（非可选）

抄 `mech-projection-analysis/references/` 里现成的，逐条对根因：

| # | 判据 | 输入字段 | 判据式 | 挡的根因 | 误报风险 |
|---|---|---|---|---|---|
| J1 | **总体尺寸唯一性** | `annotations[].role` | 每轴向 `role=overall` 的条数 ≤ 1 | #1 #7 | 低 |
| J2 | **尺寸链闭合** | `annotations[]` + `views[].bbox` | Σ增环 = 总体；判「闭合/多标/漏标」 | #1 #7 | 中（现有 `s5b` 已有，需加角色） |
| J3 | **投影压缩律** | `lines[]` + `views[]` | 斜面标注实长 = 投影长 / cos(倾角)；两视图推不出同一 r → 报 | #2 | 中 |
| J4 | **轮廓厚度取中段** | `layers` + `lines[]` | 厚度 = 成对平行线间距的**中位数**；端部被圆角切线处不计 | #3 | 低 |
| J5 | **剖面线断口 = 孔/槽** | `layers.section` + `features[]` | 有剖面线 = 材料；无剖面线封闭区 = 空处；断口位置必须有对应 feature | #5 | 低（矢量路线准） |
| J6 | **可见性原则** | `layers.center/fine` | 内腔轮廓在主视图应为虚线；见实线内腔 = 是外部台阶 | #4 | 中 |
| J7 | **三角色互斥** | `annotations[].role` | 同形体同轴向的定形/定位尺寸不得互推 | #4 | 低 |

**接线要求（硬性）**：

- `skill_advice` 从 `?` 可选改成**必填**，缺文件即报错；
- `pipe.py` 的 `s0b` in_files 真正声明它；
- 判据在 `s0b` 里跑，**不放 `s0_plan`**——`s0_plan` 不接触原始图元。

> J3/J4/J6 是"形状/位置"类判据，项目自己的经验
> （`drawing_techniques.md` §五第 9 条：「形状、相对位置这类错误，数值校核往往抓不到」）
> 说的正是这类。但注意：**这类判据必然有误报**，所以第 0 期的锚点是它们的前提。

### 第 4 期：锚点（与第 2/3 期并行，不是之后）

`s6_compare` 的基准从「只有 `ref_spec`」改成**双基准**：

| 基准 | 来源 | 独立性 | 覆盖 |
|---|---|---|---|
| 现有 | `ref_spec.py`（人抄） | 与模型同源人抄 | 全部零件 |
| 新增 A | `dwg_semantics` 的实测外接 + 标注值（机器量） | 机器量 vs 人抄，两条路径互校 | 有语义产出的零件 |
| 新增 B | 客户真值 STEP | **完全独立** | 仅 11/42 件（另一台机器核实） |

**为什么不能等**：J1~J7 都是"会误报"的规则。没有锚点时，你分不清"规则抓对了"还是"规则乱报"——
**误报会淹掉真报**。锚点是让判据可信的前提，不是收尾工作。

这和另一台机器自己 T1 那条（「先看真值 face census，再决定要不要读 2D」）是同一个逻辑，
它只是没把这逻辑应用到自己的改造排序上。
