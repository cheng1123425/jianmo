# 分步实施计划：让「改架构不再重写产品」

> 目标一句话：**新增一个零件，全程不写一行 Python；改架构，产品层 0 个文件需要动。**
>
> 配套文档：`MSG.md §〇 接口演进纪律`（规矩）、`docs/遗留事项与下一步.md`（历史债清单）。
> 本文件是这两份的**执行手册** —— 每一步都写清「改哪个文件 / 谁来写 / 怎么验证」。
>
> 状态标记：✅ 已完成 · ⬜ 未开始 · 🔶 进行中
> 成本标记：**[代码]** = 脚本跑，0 token；**[AI]** = 需要读代码改代码，消耗 token

---

## 〇、为什么是这个顺序

```
阶段 0 立规矩   →   阶段 1 解耦   →   阶段 2 版本化   →   阶段 3 发布
（把纪律变成机制）  （把产品变成数据）  （让老数据能升级）  （对外承诺）
```

**不能跳阶段。** 跳过阶段 0，阶段 1 解耦完的成果会被后来的架构改动重新破坏掉，前功尽弃。
跳过阶段 1 直接做阶段 2，等于给一堆"还是代码"的产品打版本号 —— 版本化的是代码不是数据，白做。

## 阶段 2 · 版本化 —— 让老零件在新架构下继续跑（1~2 周）

> 这一段解决「V1 的零件在 V2 架构下怎么办」。

| # | 步骤 | 成本 | 说明 |
|---|---|---|---|
| 2.1 | 给三类数据加 `schema_version`：`ir.json` / `dims_spec.py` / `draw_spec.py` | **[AI 少量]** | 现在是 `protocol: "mpipe/1"` 版本不符即拒绝 |
| 2.2 | 写迁移器 `tools/migrate.py`：V1→V2 缺字段给默认值、改名字段做映射 | **[AI 一次]** 约 150 行 | **从"拒绝打开"改成"自动升级"** |
| 2.3 | `manifest.json`：只存引用（文件路径 + 版本 + 变换矩阵），**绝不存几何** | **[AI 一次]** | 多零件成套出图时版本混用就不是问题 |
| 2.4 | `tools/version_health.py`：扫全部零件输出体检表 | **[AI 少量]** | 替代手工维护 README 那张表 |
| 2.5 | `pipe.py --all --loop`：一条命令跑全部零件闭环 | **[代码]** | 行为变更时必须全量重跑（纪律 §4） |
| 2.6 | **合回 `main`**，打第一个版本标签 | **[代码]** | `git tag v1.0` |

**2.2 的迁移器要处理的三类差异**

| 差异类型 | 例子 | 处理 |
|---|---|---|
| 新增字段 | V2 多了 `draw_spec.schema_version` | 给默认值 |
| 改名字段 | `dims_spec.cat` → `dims_spec.category` | 映射表 |
| 语义变更 | 某字段单位 mm → cm | **不做自动迁移，报错让人确认** |

**验收标准**：把一个 V1 的 `ir.json` 丢进 V2 架构，能自动迁移并跑通闭环。

**只有两种改动还会消耗 AI**：
1. 架构新增能力（本来就该写新代码）
2. 新零件的数据文件（本来就该有人填）

## 附：三个不要做

1. **不要跳过阶段 0 直接解耦** —— 解耦成果会被后续架构改动重新破坏
2. **不要在阶段 1 完成前引入 SemVer** —— 版本化的是代码，不是数据，白做
3. **不要在没有像素对比的情况下迁移标注** —— 图纸差异肉眼极难发现，必须用 `tools/diff_images.py`
