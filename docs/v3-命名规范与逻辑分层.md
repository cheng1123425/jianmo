# v3 · 命名规范与逻辑分层

> 对象：`jianmo` 参数化建模流水线
> 目的：把**变量命名**统一到一套可被机器检查的规则；把**产品逻辑（零件专属）**与**系统逻辑（框架通用）**从"混装 + 复制粘贴"改成"分层 + 声明式"
> 日期：2026-10-14

---

## 0. 结论速览

三个动作，按风险从低到高：

| # | 动作 | 收益 | 风险 |
|---|---|---|---|
| **1** | 参数名加**轴向后缀** + 数值不出现在名字里 | 从根上堵死"把 X 向宽度当 Z 高度用"这类静默 bug | 低（纯改名，闭环可回归验证） |
| **2** | `s4/s7/s5/s8` 整步共享，`s2/s3` 抽骨架到 `lib/`；零件只留声明 | 每零件 8 步 ≈ 950 行 → ≈ 300 行；改一处全局生效 | 中（要同步改 guard 白名单） |
| **3** | 根目录的**垫片搬进 `parts/gasket/`** | 根目录只剩框架，不再"既是框架又是零件" | 低（目录搬迁） |

**最值钱的一条**：**带方向的尺寸，名字里必须带轴向。**
ybracket 那个 `58 ≠ 48` 的建模 bug（`HANDOFF-2026-10-14.md` §3），根因就是
`hw = WALL_W / 2` 被当 Z 高度用了 —— `WALL_W` 是 X 向宽度。如果这个参数叫
`WALL_W_X`，局部变量叫 `half_w_x`，那么写 `Polyline(..., (0, half_w_x))` 的一瞬间就该警觉：
**"我为什么拿 X 向的半宽去当 Z 坐标？"** 命名有轴，这个 bug 写不出来。

## 1. 现状诊断

### 1.1 四个零件，四套命名风格

| 位置 | 样本 | 风格特征 |
|---|---|---|
| 根 `params.py`（垫片） | `R_OUT_CEN` `R_SIDE` `D_SIDE` `H_WING` `BASE_T` | 部位+量，**无轴向** |
| `parts/bracket` | `L` `W` `T` `ARM_T` `HEAD_Y` `HEAD_Z` `D_9` `PITCH9` `D_CB` | 单字母 + **数值进名** |
| `parts/lbracket` | `BASE_L` `BASE_T` `WALL_T` `WALL_L` `WALL_H` `WIN_W` `D_HOLE` | 部位+量，**无轴向**，`L/W` 有反用 |
| `parts/ybracket` | `LEN_X` `DEPTH_Y` `HEIGHT_Z` `WALL_W` `BASE_TAPER_Y0` | **唯一带轴向**，但只此一家 |

**同名不同义 / 同义不同名**（这才是真正的成本）：

| 概念 | 垫片 | bracket | lbracket | ybracket |
|---|---|---|---|---|
| 底板厚 | `BASE_T` | `T` | `BASE_T` | （无，用 `WALL_T`+`ARM_T`） |
| 底板 X 向长 | `L`（派生量） | `L` | `BASE_L` | `LEN_X` |
| 底板 Y 向宽 | `W`（派生量） | `W` | `BASE_W` | `DEPTH_Y` |
| 板厚（X 向） | — | `ARM_T` | `WALL_T` | `WALL_T` |
| 孔的直径 | `D_HOLE_CEN` `D_HOLE_SIDE` | `D_9` `D_PIN` `D_CB` `D_CS` | `D_HOLE` | `D_THRU` `D_CBORE` |

**特别注意 `L` / `W` 的反用**：`lbracket` 里 `WALL_L` 是 **Y 向宽**，但 `L` 在全项目其它地方都表示"长"。同一个字母在两个零件里表示正交的两个方向，跨零件读代码必错。

### 1.2 三个具体的命名缺陷（都会直接致 bug）

| 缺陷 | 实例 | 后果 |
|---|---|---|
| **数值进名字** | `D_9`、`PITCH9`（`bracket`） | 把 φ9 改成 φ10，名字就成了谎话；要么改一遍全项目，要么名字永久说谎 |
| **`D` 既表示直径又表示距离** | `D_SIDE`（垫片）实为"侧凸台**中心距**" | 与 `D_HOLE_SIDE`（**直径**）并列时读者无法区分 |
| **无轴向** | `WALL_W`、`BASE_L` | 轴混淆 bug 静默通过（见 §0） |

### 1.3 分层：只分了"谁自带"，没分"文件内部"

项目已经有 `SHARED_STEPS`（5 个零件无关步骤回落根目录）vs 零件自带 `s1~s8`，这个**划分是对的**。
但 `s1~s8` **内部**仍然是"系统骨架 + 零件差异"混装，靠**复制粘贴**分发到各零件。实测重复率：

| 步骤 | 文件行数 | 与 lbracket 的差异行 | 两零件相似度 | 判定 |
|---|---|---|---|---|
| `s4_table` | 165 | 11 | **93%** | 系统骨架为主 |
| `s7_decide` | 64 | 7 | **89%** | 系统骨架为主 |
| `s5_collect` | 50 | 10 | **80%** | 系统骨架为主 |
| `s8_apply` | 45 | 13 | **71%** | 系统骨架为主 |
| `s2_drawing` | 250 | 121 | 52% | 半骨架半产品 |
| `s3_render` | 208 | 130 | 38% | **多为"分叉"**（见下） |
| `s6_compare` | 85 | 75 | 12% | **产品逻辑为主**（校验项清单） |
| `s1_build` | 91 | 153 | 近乎零 | **纯产品逻辑**（几何构造） |

**读法（两条，都很关键）**：

1. 相似度 ≥70% 的 4 步（`s4` `s7` `s5` `s8`）**共用同一份骨架**。改了要改 4 遍，漏一处就是
   "一个零件修了、其余三个没修"。这是**复制粘贴分发**的直接成本。

2. ⚠️ **相似度低 ≠ 真有零件差异**。实测 `s3_render` 那 130 行差异里，大部分是**分叉**：
   `lbracket` 修好了「边归一化」的 bug（改用整视图 `ey_min/ey_max` 统一归一），
   而 `bracket` / `ybracket` **还留着旧的逐边归一写法** —— 同一个 bug，
   修进了一个零件，另外几个没跟上传导。**这才是复制粘贴最贵的代价：修复不会自动传播。**

### 1.4 根目录"既是框架又是零件"

`pipe.py` / `msgio.py` / `guard.py` / `steps/{s0,s0b,s5b,s6b,s9}` 是**框架**；
而根的 `params.py` / `dims_spec.py` / `ref_spec.py` / `steps/{s1..s8}` / `notes/` / `models/` 其实是**垫片这个零件**。

后果：
- 跑 `python pipe.py`（不带 `--part`）跑的是垫片 —— 但文档里它读起来像"通用入口"
- 框架升级时很容易误碰垫片的同名文件（两份 `steps/s1_build.py`，一份框架一份零件）
- 新增零件时，"从根目录复制"会连垫片的**零件内容**一起复制（README 已警告过这个坑）

**正确形态**：根目录 = 纯框架；垫片 = `parts/gasket/`。

### 1.5 还有第三类逻辑没被命名

除了"系统"和"产品"，还有一层**领域知识 / 工程判据**，它既不依赖框架、也不专属某个零件：

- 投影原则（长对正 / 高平齐 / 宽相等）→ `s6b_projection`
- 尺寸链闭合算法 → `s5b_dimchain`
- 图纸解析（几何层 / 标注层 / 接地层）→ `tools/dwg_parser`
- 平面端面标高系统性测量 → `tools/facelevels`

这类东西现在是"零件无关步骤 + tools"，归类正确但**没有名字**，容易被当成系统逻辑混在 `pipe.py` 一类文件里。建议显式命名为**领域层**，将来还能被别的项目（比如 `Zero-to-CAD` 验证报告）复用。

## 2. 命名规范

### 2.1 参数命名四段式

```
<部位>_[<修饰>_]<量型>[_<方向>]
 BASE     NOSE      R     0
```

- **部位**（必选，封闭集合）：`BASE`(底板) / `WALL`(立板·背板) / `ARM`(臂) / `EAR`(耳) /
  `HEAD`(圆头) / `WIN`(窗口) / `OPENING`(开口) / `BOSS`(凸台) / `NECK`(凹颈) / `CEN`(中心) /
  `CBORE`(沉孔) / `PIN`(销孔) / `HOLE`(孔) / `BODY`(总体包络)
- **修饰**（可选，可多层）：`NOSE`(圆头) / `END`(末端) / `TOP`(顶部) / `INNER`(内侧) /
  `FRONT`(前端) / `THRU`(贯通) / `CHAMF`(斜切) / `TAPER`(斜削) / `0`(起点)
- **量型**（必选）：见 §2.2 词表
- **方向**（该尺寸沿某轴有明确方向时**必写**）：`X` / `Y` / `Z`

**示例**：
`BASE_L_X`（底板 X 向长）· `BASE_NOSE_R`（底板圆头半径）· `ARM_END_Y`（臂末端 Y 坐标）·
`CBORE_T_Z`（沉孔 Z 向深）· `EAR_HOLE_P`（耳孔中心距）· `CEN_ARC_R`（中心弧半径）

### 2.2 量类型词表（封闭集合，不得新增）

| 词 | 含义 | 单位 | 必带轴向？ |
|---|---|---|---|
| `L` | 长度（沿某轴的尺寸） | mm | ✅ |
| `W` | 宽度（沿某轴的尺寸） | mm | ✅ |
| `T` | 厚度 | mm | ✅ |
| `H` | 高度（自基准面起算） | mm | ✅ |
| `C` | 坐标 / 定位（沿某轴的位置） | mm | ✅ |
| `GAP` | 间距（两特征之间，非中心距） | mm | ✅ |
| `R` | 半径 | mm | ❌ |
| `D` | **直径**（不允许表示距离） | mm | ❌ |
| `P` | 中心距 / 节距（pitch） | mm | ❌ |
| `ANG` | 角度 | ° | ❌ |
| `N` | 数量 | 个 | ❌ |

> **必带轴向**的 6 个量型（`L` `W` `T` `H` `C` `GAP`）都是「沿某轴量出来的」，名字里必须写 `X`/`Y`/`Z`。
> `R` `D` `P` `N` `ANG` 本身不含方向，不带轴向后缀。

### 2.3 方向后缀规则（本项目最重要的一条）

**判据**：这个尺寸沿哪个轴"量"出来的？如果答案是唯一确定的轴，就必须把轴写进名字。

| 情形 | 要写轴 | 例 |
|---|---|---|
| 沿 X/Y/Z 的线性尺寸 | ✅ | `BASE_L_X`、`BASE_W_Y`、`HEIGHT_Z` |
| 板厚（板的法向量即厚度方向） | ✅ | `WALL_T_X`（立板厚，沿 X） |
| 某轴上的坐标 / 标高 | ✅ | `WIN_Z0`、`HEAD_C_Z` |
| 直径（本身无方向） | ❌ | `SIDE_HOLE_D` |
| 半径（本身无方向） | ❌ | `EAR_R` |
| 中心距（本身无方向） | ❌ | `EAR_HOLE_P` |

**反例 → 正例**：

```python
# ✗ 轴混淆的温床
WALL_W = 116.0
...
hw = WALL_W / 2
Polyline((0, 0), (taper_y1, 0), (taper_y1, hw_f), (P.BASE_TAPER_Y0, hw), (0, hw))
#                                                  ↑ 拿 X 向半宽当 Z 坐标，静默变成 58 而不是 48

# ✓ 写不出来的 bug
WALL_W_X = 116.0          # 背板/中央块 X 向宽
...
half_w_x = WALL_W_X / 2
Polyline(..., (BASE_TAPER_Y0_Y, BASE_H_Z), (0, BASE_H_Z))
#                                    ↑ half_w_x 根本不该出现在 Z 坐标位
```

### 2.4 代码内部变量

| 规则 | 说明 |
|---|---|
| 几何中间量必须带轴 | `half_w_x` / `t_up_y` / `angle_lower_deg`，不用 `hw` / `a_dn` |
| 循环变量避开保留名 | 不用 `it`（与轮次变量冲突，已出过一次致命 bug，见 `系统梳理.md` §8）；用 `x` / `item` / `chk` |
| 私有 helper 前缀 `_` | `_load_json_opt` / `_fmt` |
| 模块级常量 UPPER_SNAKE | `PLOT` / `TOL` / `MARKS` |
| 单位进变量名后缀（仅在混用风险时） | `_deg`（角度）、`_mm`（默认省略，全项目统一 mm） |

### 2.5 消息 `data` 的 key

**规则**：跨步骤产出必须**命名空间化**，不允许把裸 `issues` 这类通用键平铺到顶层。

```python
# ✗ s6b 与 s6_compare 都吐 "issues"，in_data_from 平铺合并时互相覆盖 → s7 必 KeyError
return [], {"issues": [...]}

# ✓ 命名空间隔离（项目已经在做，推广到所有跨步骤协议）
return [], {"projection": {"n_ok": 2, "issues": [...]}}
return [], {"dimchain":   {"n_chains": 3, "issues": [...]}}
```

**键名规范**：`<阶段语义>_<内容>` 或嵌套一层。跨步骤消费方**显式按键取**，不遍历顶层。

## 3. 三层划分

### 3.1 三层定义与一句话判据

| 层 | 判据 | 换零件要改吗 | 换框架要改吗 |
|---|---|---|---|
| **S 系统层**（框架） | "不含任何零件几何与工程判据，只负责跑、传、缓存、隔离、渲染" | ❌ 不改 | ✅ 改这里 |
| **D 领域层**（工程判据） | "讲的是机械制图/几何的通用规律，与具体零件无关，但换项目就没用" | ❌ 不改 | ❌ 不改（可复用到别的 CAD 项目） |
| **P 产品层**（零件） | "说的是这个零件长什么样、要标注什么、跟原图差在哪" | ✅ 只改这里 | ❌ 不改 |

**快速自测**：把这段代码贴到另一个零件（比如把 bracket 的换到 ybracket）——
- 原样能用 → **S 系统层**
- 原样能用但只在 CAD 项目里有用 → **D 领域层**
- 必须重写 → **P 产品层**

### 3.4 s1~s8 抽骨架：具体怎么切

以 **`s2_drawing`（250 行，两零件相似度 52%）** 为例。现在零件文件里这些段落是**系统骨架**：

| 段落 | 现行位置 | 应去 |
|---|---|---|
| `p()` / `_y()` / `PLOT` / `visible()` / `first_circle_r()` | 零件文件头部 | `lib/drawing_fc.py` |
| `add_dia` / `add_rad` / `add_distx` / `add_disty` / `add_extent` / `_rec` | 零件文件中部 | `lib/drawing_fc.py` |
| `edges_json` / `circles_json` / `hlines_json` | 零件文件尾部 | `lib/drawing_fc.py` |
| `boot/ref_path/exec_module` 样板 | 零件文件头部 | `lib/drawing_fc.py` 里的 `run(...)` |
| **`# ---- Front ----` / `# ---- Right ----` / `# ---- Top ----` 三段标注布置** | 零件文件 | **留零件 = `marks.py`** |

抽完后，零件 `s2_drawing.py` 缩成：

```python
# parts/bracket/steps/s2_drawing.py
from lib.drawing_fc import build_drawing

if __name__ == "__main__":
    build_drawing("s2_drawing", MARKS)
```

`marks.py` 是**声明式**的：

```python
# parts/bracket/marks.py
MARKS = [
    # (视图,  类型,   引用,                          纸面位置,      语义 label)
    Mark("Front", "disty", ("H_boss", ),              (156.7, 60.8), "head_h"),
    Mark("Top",   "dia",   ("BASE_HOLE_D",),          (90, 64),      "D9"),
    Mark("Front", "rad",   ("HEAD_R",),               (30, 70),      "R_head"),

```

同样的切法：

| 步骤 | 系统性部分（→ `lib/`） | 产品性部分（留零件） |
|---|---|---|
| `s3_render` | FreeCAD→matplotlib 落盘、图框、比例 | 视图挑选顺序（若有差异） |
| `s4_table` | 表格排版、OK/`!!` 比对渲染 | `dims_spec.DIMS`（已是声明式 ✅） |
| `s5_collect` | 从 `_drawing.json` 提外接/圆/高度层 | 几乎无（可整步共享） |
| `s6_compare` | `add()` / 容差比较 / 判定汇总 | **`CHECKS` 校验项清单** |
| `s7_decide` | 三路校验分级策略、`suppress_autofix` | 无（可整步共享） |
| `s8_apply` | 写回 params、格式保持 | 无（可整步共享） |

`s6_compare` 抽完的样子：

```python
# parts/bracket/steps/s6_compare.py
from lib.compare import run_checks

CHECKS = [
    Check("geom", "俯视外接 X (底板长)", ref=("TOP", "len_x"), cur="len_x_top",
          note="底板长 = BASE_L_X"),
    Check("geom", "外接 Y (含圆头)",     ref=("TOP", "len_y"), cur="len_y_top",
          note="外接 = -HEAD_C_Y + ARM_END_Y + HEAD_R"),
```

**顺带治好 ybracket 的结构性失明**：`s6_compare` 现在只读 `R.TOP` / `R.FRONT`，不读 `R.RIGHT`（`HANDOFF` §4）。
把 `CHECKS` 外化成清单后，加一条"面到面距离"检查就是往清单里加一行，而不是改 85 行逻辑 —— 领域层的 `domain/facelevels.py` 已经能提供这些数据。

## 4. 其他会咬人的点（顺带补上）

### 4.1 参数分三级，别混在一起

| 级别 | 定义 | 谁能改 | 例 |
|---|---|---|---|
| **主参数** | 人直接输入、图纸上标的 | 人 | `BASE_L_X` `WALL_T_X` `EAR_HOLE_P` |
| **派生量** | 由主参数算出，**不进 params.py** | 代码 | 总长 = `2*(SIDE_BOSS_P + SIDE_BOSS_R)` |
| **构造量** | 只决定图形，图上不标 | 代码 | 凹颈圆心（`dims_spec.neck_center`） |

现在 `params.py` 里只有主参数 ✅，但**没有显式声明"哪些是派生量"** ——
`dims_spec.py` 用 `key=None` 隐式表示。建议 `dims_spec.py` 加 `kind` 字段：
`kind="direct"` / `"derived"` / `"construct"`，让工具能自动区分。

### 4.2 参数 schema 自检（治 bug 的根）

ybracket 的 `58≠48` 之所以能发生，是因为 `s1_build` **读了一个语义不符的变量**且没人拦。
建议：`params.py` 末尾声明 **`__schema__`**，`s0_plan` 启动时校验：

```python
__schema__ = {
    "version": "1",
    "axes": {"WALL_W_X": "X", "WALL_T_Y": "Y", "BASE_H_Z": "Z", ...},
    "units": "mm",
    "origin": "背面·底面·对称中心",
    "required": ["BASE_H_Z", "EAR_R", "CBORE_T_Z"],
    "positive": True,          # 所有尺寸必须 > 0
}
```

配合一条静态检查：`s1_build` 里出现 `Polyline(..., (a, b))` 且 `b` 来自 `*_X` 的参数 → 报警。
这比事后闭环迭代便宜得多（而且如 `HANDOFF` §4 所述，闭环**改参数永远修不了"读错变量"**）。

### 4.3 坐标系契约（每个零件必须写）

`ybracket` / `lbracket` 的 `params.py` 头部已经写了坐标系定义 ✅（"原点 = 背面·底面·对称中心"），
垫片和 bracket **没写**。改为**强制**：`params.py` 的 docstring 必须含一段 `坐标系：` 说明原点与各轴正向。

不写的后果：`s2_drawing` 的视图 y 轴方向"不保证"（README 踩坑 #3 已记录主视图出现过 `y=50−z` 也出现过 `y=z−50`），
根因之一就是零件没声明原点，出图侧只能猜。

### 4.4 单位契约

全项目统一 **mm**，名字里不写单位（`_mm` 不出现），只在文档与 `__schema__["units"]` 声明一次。
角度参数例外，必须带 `_deg`（`ANG_*` 词已经表达，可不重复）。

### 4.5 错误分类编码

`notes/errors.md` 现在是自由文本 + 分类去重。建议给固定编码，便于统计与跨零件比对：

| 码 | 类别 | 例 |
|---|---|---|
| `E-AXIS` | 轴混淆 | ybracket 底座 58≠48 |
| `E-VAR` | 读错变量 | 硬编码 `42.0/2.0` 而不用 `EAR_R` |
| `E-REF` | 边引用错 | `References2D` 0-based 下标 |
| `E-GEOM` | 几何不成立 | 孔径 > 凸台径 |
| `E-DIM` | 尺寸链不闭合 | |
| `E-PROJ` | 投影原则违规 | |
| `E-CALIB` | 图纸标定偏差 | |

`s9_record` 归类时按这个表打码，将来能一眼看出"这个项目最容易犯哪类错"。

### 4.6 版本契约

`params.py` 的 `__schema__["version"]` + `msgio.PROTOCOL`（`mpipe/1`）要联动：
零件的 `__schema__` 版本与框架期望不符时，`s0_plan` 应直接报错而不是跑出错误结果。

### 4.7 命名空间要推广到所有跨步骤 data

现在只有 `s5b`→`dimchain`、`s6b`→`projection` 做了命名空间。
`s5_collect` / `s6_compare` 的产出仍是裸键（如 `issues`），`s7_decide` 靠注释约定消费。
建议统一：**所有 `out.data` 顶层键都带阶段前缀**（`s5_` / `s6_` …），`in_data_from` 平铺合并后不会误撞。

## 5. 迁移路径（三刀，每刀独立可验证）

### 第 1 刀 · 改名（低风险）✅ **已执行（2026-10-14）**

> 执行结果、验证证据、系统层零改动证明 → 见 **`v4-第2-3刀方案（待批）.md` §1**
> 工具：`tools/rename_params.py`（tokenize 标识符级替换）｜映射表：`docs/rename_maps/*.json`

1. 按 §2.6 对照表改各零件 `params.py`
2. 联动改 `dims_spec.py`（`key=` 字段、`expr=lambda P: P.xxx`）、`ref_spec.py`、`steps/s1_build.py`、`steps/s2_drawing.py`、`steps/s6_compare.py`
3. 注意 `guard.py` 会拦"硬编码盘符"等，改名不触发

**验证**：`python pipe.py --part parts/<零件> --loop` 仍 `pass`；`python guard.py` 仍全绿。
**关键**：改名**只改标识符**，不改任何数值。跑出来 `drawing.pdf` 的数值应与改名前逐字节一致。

### 第 2 刀 · 抽骨架（中风险）

按相似度分**三种**处理，不要一律"抽 lib"：

**A. 相似度 ≥70% → 整步提升为 SHARED（最省事，收益最大）**

`s4_table`(93%)、`s7_decide`(89%)、`s5_collect`(80%)、`s8_apply`(71%) ——
这四步逻辑本就是通用的，零件文件只是垫片的副本：

1. 用 `diff` 逐对核对这 4 步在 4 个零件里**有没有分叉**（`s3_render` 的教训就在眼前）
2. 取确认一致的版本为权威版，放回 `steps/`
3. 把这四个名字加进 `pipe.py` 的 `SHARED_STEPS`
4. 删掉 4 个零件里的对应文件
5. 跑全量闭环

**收益**：一次消掉 4 个零件 × 4 步 ≈ 1300 行重复代码。

**B. 相似度 30–70% → 抽 `lib/`，零件只留声明**

`s2_drawing`(52%)、`s3_render`(38%)：骨架抽到 `lib/drawing_fc.py` / `lib/render_pdf.py`，
零件只留 `marks.py`（见 §3.4）。

**C. 相似度 <30% → 留零件，只抽明显通用的小函数**

`s6_compare`(12%)、`s1_build`(近乎零)：这两步本身就是产品逻辑，别硬抽。

**每步验证**：`python pipe.py --part parts/<x> --loop` 对 4 个零件全 `pass`；
`python guard.py` 全绿；`docs/flowchart.md` 拓扑不变。

**⚠️ 关于 `guard.py`**：现在的规则不含"禁止 import lib"，但会拦 `from s\d+_ import`。
抽骨架后零件文件会 `from lib.xxx import yyy`，需确认 guard 白名单（`lib` 不在 `s\d+_` 模式内，✅ 不会被误拦）。

### 第 3 刀 · 垫片搬家 + 目录定稿（低风险）

1. 根目录的 `params.py` / `dims_spec.py` / `ref_spec.py` / `steps/s1~s8` / `notes/` / `models/` / `drawing.*` / `dims_table.*` / `_msg/` / `_drawing.json` → `parts/gasket/`
2. 根 `steps/` 只留 5 个 SHARED 步骤
3. `README.md` / `MSG.md` / `方案设计/系统梳理.md` 同步更新（去掉"根目录是垫片"的说明）
4. `pipe.py` 默认 `--part` 改成 `parts/gasket`（或不带 `--part` 时报错提示）

**验证**：`python pipe.py --part parts/gasket --loop` pass；`python pipe.py` 给出明确提示而非跑垫片。

## 7. 一页总结

**命名**：`部位_修饰_量型_方向` 四段式；**带方向的尺寸必须写轴**；`D` 只表直径；数值不进名。
**分层**：S 系统层（`lib/` + `steps/` + `pipe/msgio/guard`）／D 领域层（`domain/`，制图规律，可移植）／P 产品层（`parts/<零件>/`，只留 `params` + 声明清单 + `s1_build` + `s6_compare` 清单）。
**判据**：贴到另一个零件能用 → S；能用但只在 CAD 有用 → D；必须重写 → P。
**顺序**：先改名（低风险），再抽骨架（收益最大），最后搬垫片（收尾）。
